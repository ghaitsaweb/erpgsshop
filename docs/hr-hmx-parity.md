# HMX Human Resources Functional Parity Matrix

This matrix tracks the existing ERP GSSHOP Django HR implementation against HMX business behavior. The HMX source reference is kept locally and is not committed or deployed; copying source does not change the `PARTIAL` or `GAP` status of the existing Django implementation.

- Historical HMX baseline for the matrix: the runtime formerly serving port 8000 from `/home/yusufmjt/hmx-human-resources-latest/hmx`, branch `fix/expense-advance-seed-and-my-loan-center`, commit `eca519e` (19 commits after the earlier `77169d3` comparison point). The copied source snapshot uses the later `origin/Human-Resources` commit `c42f10233ba6d3e366eb3ac07b1a4ff4a97d34f1`.
- GSSHOP implementation base: this repository, branch `main`, through commit `b7ddf0f`; the HR02 evidence below also describes the current implementation under review.
- HMX paths below are relative to `hmx/module/basic/`; GSSHOP paths are relative to this repository.
- This is a source-code audit. The scenarios below are acceptance criteria, not claims that an HMX runtime comparison has passed.

`PARTIAL` means a usable model or screen exists but at least one named HMX business outcome is absent or unverified. `GAP` means the named end-to-end flow has no equivalent implementation found. No row is marked `MATCH` until its data, action, access, and output are exercised against comparable fixtures in both systems. The GSSHOP catalog already labels HR, Payroll, Recruitment, and Talent as `beta` (`modules/apphub/catalog.py`).

## Comparison contract

Use one shared scenario sheet per row. Each sheet must record preconditions, actor/role, company/branch, input, action sequence, HMX result, GSSHOP result, error path, and cleanup or rollback of test data. Compare values and side effects, not only HTTP `200`, visible menu labels, or final status.

Minimum fixtures: two companies, two branches per company, employee/self-service user, supervisor, HR manager, and payroll administrator; employees with different contracts, schedules, leave balances, and effective dates. Exercise cross-company access, duplicate submissions, concurrent approvals, timezone/date boundaries, and reversal. Use a test database or disposable fixture, never the live ERP database for parity scenarios.

The existing GSSHOP tests in `core/tests.py` verify HR navigation/CRUD exposure, guarded status transitions, training conduct screens, role scope, and a training list query-growth case. These are valuable foundation checks but do not prove the business outcomes in the matrix. HMX has focused tests under `core_hr/tests/` and the dependent module test directories; select the corresponding behavior as the expected contract and verify it with the HMX runtime before calling any row `MATCH`.

For new ORM/data paths, review SG001–SG004 (batch queries, bounded reads, batched writes, ORM invalidation). Add query-growth tests where recordset size can increase the query count. Run the repository's configured checks and Scale Guard before any agent-made commit, using the applicable baseline and staged scope.

## HR05 implementation update — 25 October 2026

The leave request now selects a company leave type rather than relying on its display name. Submission calculates full or half days using either calendar days or the employee's active work schedule and company holidays, checks an active contract and overlapping requests, and reserves approved yearly allocations in one transaction. Rejection and future-dated cancellation restore the same allocation once, with linked movement rows and workflow audit details. A leave type that requires evidence can receive a scoped attachment stored in the database. Submitted requests, approved allocations, and generated movement rows cannot be edited through the workspace.

The HR05 code now creates dated FIFO leave buckets from approved allocations, records exact bucket consumption, checks gender, tenure, notice, duration, past dates, cooling periods, and blackouts, and expires unused bucket days in bounded, resumable batches. Expiry preserves days already reserved by submitted encashments; a reversal after expiry forfeits restored days while protecting other reservations. Encashment requires a reason, assigns a stable reference at submission, reserves date-valid buckets, snapshots a contract or flat daily rate, posts the debit on approval, and reverses the original buckets on cancellation before payroll generation. Evidence can be required above a configurable day threshold with a per-type size limit. The workspace exposes policy and blackout configuration, read-only bucket and reservation audit rows, and a batched “Available Today” amount that accounts for expiry and pending encashment. Lists and dashboards defer binary attachment content, and Django admin cannot directly edit the leave ledger. The 31 focused leave and encashment tests pass against a temporary SQLite schema built without migrations; the combined 118-test HR and Approval Workflow suite passes on a fully migrated temporary SQLite database. The HMX source repository was read only, and no HMX runtime comparison was performed.

An opening-balance document can now be finalized once into an approved allocation, an opening-source bucket valid from its cut-off date, and separate credit and prior-use debit movements. Its available amount can then fund leave requests. The UI blocks forged status changes and editing or deletion after finalization; Django admin treats the document as ledger data. Six focused tests pass without migrations, and the combined 118-test suite passes with all migrations. The existing one-allocation-per-employee/type/year schema prevents an opening grant from coexisting with a regular grant in the same year. Legacy rows already marked finalized have no automatic ledger backfill and need review before use.

HR05 remains **PARTIAL**. HMX supports multi-line opening documents, request lines, approval matrix details, hourly leave, HR-year entitlement generation, full payroll settlement, and additional attendance/payroll effects that are not yet matched. The basic payroll generator links assigned encashments to payslips and supports simple accrual/payment accounting; complete leave and payroll settlement remains outstanding. Existing legacy requests and encashments without matching ledger rows require explicit reconciliation before their approval or reversal can use the new workflow. The source snapshot under `hmx_runtime/` remains a temporary reference; it is not the implementation served by ERP GSSHOP.
