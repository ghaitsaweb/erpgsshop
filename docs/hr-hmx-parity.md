# HMX Human Resources Functional Parity Matrix

This matrix compares observable Human Resources behavior, not source-code or visual similarity. It is a baseline for implementing ERP GSSHOP independently and for testing the same business scenarios in both systems.

- HMX baseline: `/home/yusufmjt/hmx-human-resources-latest`, branch `Human-Resources`, commit `77169d3f9c201f17984df6f5f632eb5f40eabd22`.
- GSSHOP baseline: this repository, branch `main`, commit `f8546d7ecca123b18311ce478aceed366c17da4b`.
- HMX paths below are relative to `hmx/module/basic/`; GSSHOP paths are relative to this repository.
- This is a source-code audit. The scenarios below are acceptance criteria, not claims that an HMX runtime comparison has passed.

`PARTIAL` means a usable model or screen exists but at least one named HMX business outcome is absent or unverified. `GAP` means the named end-to-end flow has no equivalent implementation found. No row is marked `MATCH` until its data, action, access, and output are exercised against comparable fixtures in both systems. The GSSHOP catalog already labels HR, Payroll, Recruitment, and Talent as `beta` (`modules/apphub/catalog.py`).

`core_hr_lms` is a compatibility shell in this HMX snapshot: its manifest states that HR Training LMS logic is owned by `core_hr`. It is therefore covered by HR10 rather than counted as a separate missing application.

HR02's first local slice covers only work email and phone. It does not yet cover HMX's other personal-data fields, one-to-many detail changes, attachment policy, or full before/after history, so it remains `PARTIAL`. The focused GSSHOP tests passed with an isolated SQLite in-memory database; a side-by-side HMX runtime scenario has not yet been run.

HR03's first local slice makes status changes workflow-only and rejects invalid dates, negative salary, and overlapping active contracts for one employee. It does not yet reproduce HMX's submitted/approval stage, compensation package, allowance history, contract letter generation, or payroll linkage. Its focused GSSHOP tests passed in the same isolated test environment.

HR04's correction slice captures the original daily attendance at submission, rejects concurrent changes and duplicate active requests for the same employee/date, applies an approved correction once, and stores before/after values in the workflow audit. Requests submitted before this snapshot feature must be recreated before approval. The focused query-growth test compares 2 and 12 existing attendance days with equal query counts; it is not a production-scale latency or index-plan benchmark. HMX's range-based correction lines, full schedule/formula recalculation, bulk raw-punch import, and payroll consequences remain unimplemented or unverified.

HR04's raw-punch slice adds a per-event Process Day action that accepts exactly one unprocessed check-in and one later check-out for one employee and one work date, with a single active assignment and same-company schedule/shift. It supports a checkout on the next local date for an overnight shift by retaining both full timestamps alongside the existing display times; the attendance list shows those timestamps, and clicking either punch processes the same work date. The assignment form validates overlapping active periods and cross-company schedules; the processor still rejects ambiguous legacy assignments. It records source punch IDs, marks both punches processed, and retains a workflow audit; existing daily records and submitted corrections are not overwritten. Raw-derived daily records are changed through a correction request, which snapshots the timestamps and preserves each punch's local date when a time is approved. The work date uses the configured server timezone, not a per-company timezone. Twenty-four-hour shifts, break punches, multiple daily pairs, work/late/overtime formulas, bulk import, automatic jobs, recomputation, and payroll effects remain unsupported. Concurrent assignment writes, production-scale latency, and PostgreSQL index plans remain unverified; query-growth tests compare 2 and 12 existing attendance days, 2 and 12 prior raw events, and 2 and 12 attendance-list rows.

## Comparison contract

Use one shared scenario sheet per row. Each sheet must record preconditions, actor/role, company/branch, input, action sequence, HMX result, GSSHOP result, error path, and cleanup or rollback of test data. Compare values and side effects, not only HTTP `200`, visible menu labels, or final status.

Minimum fixtures: two companies, two branches per company, employee/self-service user, supervisor, HR manager, and payroll administrator; employees with different contracts, schedules, leave balances, and effective dates. Exercise cross-company access, duplicate submissions, concurrent approvals, timezone/date boundaries, and reversal. Use a test database or disposable fixture, never the live ERP database for parity scenarios.

The existing GSSHOP tests in `core/tests.py` verify HR navigation/CRUD exposure, guarded status transitions, training conduct screens, role scope, and a training list query-growth case. These are valuable foundation checks but do not prove the business outcomes in the matrix. HMX has focused tests under `core_hr/tests/` and the dependent module test directories; select the corresponding behavior as the expected contract and verify it with the HMX runtime before calling any row `MATCH`.

For new ORM/data paths, review SG001–SG004 (batch queries, bounded reads, batched writes, ORM invalidation). Add query-growth tests where recordset size can increase the query count. Run the repository's configured checks and Scale Guard before any agent-made commit, using the applicable baseline and staged scope.

## Implementation order

1. Build HR01–HR03 as a reliable employee/organization/contract foundation, including HR02's approved data application and audit.
2. Complete HR04–HR06 together so attendance, leave, and overtime produce trustworthy inputs and balances.
3. Implement HR07–HR08 as a generated payroll and accounting lifecycle, then validate cross-module amounts and reversals.
4. Complete HR09–HR11 and HR15–HR16 with role, branch, and notification behavior.
5. Build HR12–HR14 and HR17–HR18 as dedicated recruitment, talent, country-policy, intelligence, and assessment-integration slices. Each slice needs its own scenario suite; a menu or model alone does not close it.

The first measurable milestone is one employee in one company moving through contract, scheduled attendance, approved leave, payroll preview, generated payslip, and accounting posting with all amounts and access checks reproducible in both systems.
